# Contributing to the JLR TDV6/SDV6 Research Project

Thank you for helping strengthen this public-interest research.

The project welcomes evidence that **supports, contradicts or corrects** the current Stage 1 findings.

## Ways to contribute

You can contribute by:

- opening a GitHub Issue with a documented vehicle case;
- submitting garage or engineering data;
- identifying a primary regulator/manufacturer source;
- correcting a factual error;
- challenging an interpretation;
- proposing a better methodology;
- submitting a pull request with source-backed improvements.

## Evidence is more useful when it is specific

For vehicle cases, please provide as much of the following as you safely can:

- model and model year;
- engine type;
- failure date;
- mileage;
- symptoms;
- diagnosis;
- whether the engine was original or a replacement/remanufactured unit;
- repair quotation/invoice;
- service-history status;
- supporting photographs or documents.

Use the [`EVIDENCE_SUBMISSION_TEMPLATE.md`](EVIDENCE_SUBMISSION_TEMPLATE.md).

## Privacy

Do not post unnecessary personal data publicly.

Please redact:

- home addresses;
- telephone numbers;
- personal email addresses;
- full VINs unless necessary;
- finance-account details;
- signatures;
- unrelated third-party personal data.

Partial VINs, engine numbers and registration numbers may sometimes be useful for de-duplication, but contributors should consider whether public disclosure is necessary. Evidence can be summarised publicly while original documents are retained privately.

## Evidence labels

Contributions should identify their source type where possible:

- **Primary document** - original JLR, regulator, warranty, retailer or engineering record.
- **Professional evidence** - workshop record, engineer report or technical statement.
- **Structured owner case** - owner account supported by dates/documents.
- **Open-source lead** - forum, article, buying guide or other material needing verification.

## Claims and language

Please distinguish between:

- what a document actually states;
- what you infer from it;
- what remains uncertain.

Avoid stating allegations of concealment, fraud, deliberate regulatory inaction or universal defect as fact unless supported by appropriate evidence.

## Garage and specialist submissions

Aggregated data is particularly valuable. Useful fields include:

- defined date range;
- number of 3.0 TDV6/SDV6 engines inspected;
- number with confirmed crankshaft/main-bearing failure;
- original vs replacement-engine count;
- mileage range;
- observed bearing-shell rotation;
- crankshaft fracture/seizure count;
- repeat-failure count;
- whether anonymised work orders can verify the numbers.

Please avoid double-counting the same vehicle across branches, referrals or repeat jobs where possible.

## Corrections

Corrections are welcome. A correction should ideally include:

1. the statement you believe is wrong;
2. the proposed correction;
3. the source supporting the correction.

Material corrections will be preserved in Git history rather than silently hidden.

## Pull requests

Pull requests should:

- be focused;
- cite sources;
- preserve the distinction between primary evidence and online signals;
- avoid unnecessary personal information;
- explain major changes in the PR description.

## Editorial principle

The purpose of this project is not to maximise the number of allegations. It is to build a record that can withstand scrutiny from engineers, regulators, JLR, courts, journalists and affected motorists.
